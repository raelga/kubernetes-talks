# WordPress on Compute Engine with private Cloud SQL

This optional lab creates **billable resources** in an approved GCP project. It deploys one Debian `e2-micro` VM, WordPress and a private MySQL Cloud SQL instance in Oregon (`us-west1`, VM zone `us-west1-b`). Terraform creates a dedicated VPC, subnet, private services access peering and firewall. The VM has an external IPv4 address for package downloads and SSH; Cloud SQL has **no public IP**. The firewall allows SSH and HTTP only from the chosen IPv4 CIDR.

This is a short-lived teaching environment, not a production design: there is no high availability, backup, HTTPS, domain name, recovery strategy or managed WordPress lifecycle. Cloud SQL is billable even if a VM qualifies for the Compute Engine Free Tier. Do not store real or sensitive content in this installation.

## Prerequisites

- Install Terraform 1.10–1.x and the [Google Cloud CLI](../README.md). Complete the [state bucket lab](../00-terraform-state/README.md); this stack uses the separate `gcp/wordpress` prefix.
- Use an approved billing-enabled project. Enable Compute Engine, Cloud SQL Admin, Service Networking, Secret Manager and OS Login APIs. Your deployment identity needs permissions to manage those resources, service accounts and secret-level IAM, and to attach the VM service account (`iam.serviceAccounts.actAs`). You also need OS Login permissions to SSH. Project or organization policies may prevent deployment; do not change them merely for this lab.
- Fixed resource names require that this lab's names are unused in the project. Use an isolated approved project when possible. The private service access allocation needs an available `/16` in the VPC address space.
- Determine your current public IPv4 address, including VPN/NAT. Use `YOUR_PUBLIC_IP/32` below and update it if it changes. TCP 22 must be reachable from that address; this lab does not configure IAP.
- Complete the [GCP Terraform sign-in](../README.md#sign-in-for-terraform), verify both the active CLI account/project and Application Default Credentials, and set `GOOGLE_CLOUD_PROJECT` to the intended project. Backend access also uses ADC and requires access to the existing bucket.

## 1. Initialize, plan and apply

From the repository root, replace the bucket name (without `gs://`) and CIDR in the following commands:

```sh
cd course/infra/labs/gcp/02-wordpress
terraform init -backend-config="bucket=STATE_BUCKET_NAME"
terraform plan -var="allowed_source_cidr=YOUR_PUBLIC_IP/32"
terraform apply -var="allowed_source_cidr=YOUR_PUBLIC_IP/32"
```

Review the plan before confirming. Cloud SQL and private services access may take several minutes to provision, followed by VM startup and package installation. If you change region or zone, they must match; pass the same overrides to plan, apply and destroy. Backend configuration cannot reference Terraform variables. If changing an existing initialized backend, follow Terraform's reconfiguration or migration prompts deliberately and do not overwrite another state.

## 2. Open WordPress safely

The application has no HTTPS. Do not submit passwords over the public HTTP endpoint. Instead, forward a local port over SSH using OS Login (replace the zone if overridden):

```sh
gcloud compute ssh wordpress-vm --zone=us-west1-b -- -L 8080:localhost:80
```

Keep the SSH session open, then visit <http://localhost:8080/> on your own computer. After startup, complete the WordPress installation promptly: until then anyone who can reach HTTP from the allowed CIDR could initialize the site. Choose a **separate, disposable WordPress administrator account and password**. They are not the database administrator credentials and are not generated by Terraform. WordPress records its site URL during installation, so keep using the same forwarded address; do not install using a public HTTP address. Do not reuse any real password. Close the SSH session when finished. The exposed HTTP port is limited to your CIDR but remains unencrypted; it is not a substitute for HTTPS.

To inspect the instance address and SQL's private address without exposing secrets:

```sh
terraform output
```

## Security and troubleshooting

Terraform generates separate database root and application passwords and eight WordPress salts. It stores them in Secret Manager and in **sensitive Terraform state**; sensitive marking hides normal CLI output, not the underlying values. Protect the GCS bucket, its version history and IAM, local state backups, plans and Terraform working directory. Never commit them or credentials. The VM's dedicated service account can access only these three individual secrets, not all project secrets. Its `cloud-platform` OAuth scope allows API calls but does not itself grant IAM permissions. The database root credential is used for bootstrap; the application uses a separate database account scoped to the WordPress database. A compromised VM can access all three secrets, including root; this is a lab trade-off, not a production secret-isolation design.

The VM retrieves secret values at startup rather than placing passwords or salts in instance metadata or Terraform outputs. WordPress connects to a local TLS tunnel; the tunnel verifies the Cloud SQL instance's server CA over the private network. The bootstrap connection also verifies that CA. Since the certificate identifies the instance rather than its private IP, this design verifies the per-instance CA rather than the IP hostname. Replacing Cloud SQL also replaces its CA and requires corresponding VM configuration.

If the page is not ready, allow several minutes and inspect startup logs over SSH:

```sh
sudo journalctl -u google-startup-scripts.service --no-pager
sudo journalctl -u wordpress-db-tunnel.service --no-pager
sudo journalctl -u apache2 --no-pager
```

Check the approved project, APIs, OS Login and CIDR, outbound access to package repositories and Google APIs, secret-level IAM, private service peering and SQL readiness. Organization firewall policies may override the VPC firewall. Avoid sharing logs or state that could contain sensitive data.

Bootstrap retries secret reads and SQL connections for a limited time, then fails closed. After fixing the cause, rerun startup with `sudo google_metadata_script_runner startup` or reboot. The tunnel service retries failures. The VM stores the application password and salts in `/var/www/html/wp-config.php` (root-owned, readable by the web-server group); protect access to the VM and disk as well as state and Secret Manager.

WordPress core files are root-owned; only `wp-content/uploads` is writable by the web server. Dashboard-based core, plugin and theme installations or updates therefore do not work. This is intentional lab hardening, not a production maintenance workflow; a persistent deployment would require a controlled update process.

## 3. Destroy and inspect costs

Destroy from the same initialized directory, with the same CIDR and any project/region/zone overrides used for apply:

```sh
terraform destroy -var="allowed_source_cidr=YOUR_PUBLIC_IP/32"
```

Review and confirm the destruction plan. This deletes the database and WordPress data, VM and disk, secrets, network and lab-managed peering; it does not remove the shared state bucket. Confirm these resources and the external IP are gone in the console. Secret Manager retention/soft deletion, GCS object versions and state backups can retain sensitive material after destroy: follow your organization's retention policy and remove only authorized lab artifacts. Keep the state bucket according to the [state lab](../00-terraform-state/README.md).

Review Cloud Billing reports and filters, including Cloud SQL instance and storage, VM, persistent disk, external IPv4, network traffic, Secret Manager and state bucket storage/operations. Set or review approved budgets and alerts. Billing data can be delayed, and budgets do **not** automatically stop spending. Check current prices before deploying; do not delete the shared project or billing account.
